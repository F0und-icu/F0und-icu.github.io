Research notes · CenturyLink OpenWrt vulnerability research

Reconnaissance

The device runs OpenWrt on MIPS32, with a backend built from Lua, NGINX, and shared libraries. Most observed public-facing devices exposed only port 443, making it the main entry point for analysis. Useful background and prior research: GitHub - Ansuel/tch-nginx-gui: Modified file to apply to a stock technicolor GUI Rooting Type 2 - Hacking Technicolor Gateways GitHub - pedro-n-rocha/secr GitHub - full-disclosure/FDEU-CVE-2020-1FC5: Telia Technicolor TG389ac v.17.1.7992 Samba privilege escalation exploit

Auth

Requests pass through:

CODE
nginx(/etc/nginx/nginx.conf)-> access_by_lua

The relevant components are:

CODE
lua_package_path ';;${prefix}lib/lua/?.lua';
lua_package_cpath '${prefix}lib/lua/?.so';

lua_package_path /usr/lib/lua/?.lua

NGINX's Lua module search location is configured by lua_package_path.

The Lua backend authentication configuration is in /etc/config/web. Example configuration:

CODE
config user "usr_admin"
	option name "admin:admin"
	option role "admin"
	option gak_id "1"
	option password_disabled "0"

config rule 'clink_csrf'
	option target '/CSRF'
	list roles 'guest'
	list roles 'admin'
	list roles 'support'

Configuration behavior: [OpenWrt Wiki] The UCI system Routes configured for encrypted transport accept only encrypted requests. The original notes refer to the authentication scheme as SAP: An introduction to SAP secure remote password authentication.

Vulnerability research

Authentication analysis identified two main accounts on the device. The accounts are admin and support. The support role has more privileges, but its password was not supplied, and it uses a different login page. Captured login requests used the identity I=admin:admin for the normal page and I=support:xxxx through sc_login.html. The authentication flow suggests that the first identity component denotes the role. The relevant configuration is in /etc/config/web:

CODE
config user "usr_support"
	option name "support:Century2016$"
	option role "support"
	option interface "lan"

Related permissions in /etc/config/clash:

CODE
config user 'engineer'

Following these clues led to password generation in /etc/uci-default/tch_0071-web.passwords.

SH
if [ "$USER" == "all" -o "$USER" == "usr_support" ]; then
    local key="$(uci get env.var.prod_number)!#$(uci get env.var.serial | tail -c 7)"
    _set_key "usr_support" "${key}"
    # Save the password to temporary storage for configuring CLASH

The generation logic is:

CODE
prod_number+'!#'+ serial[-7:]

prod_number is stored in /etc/config/env.

    option prod_friendly_name 'CenturyLink C1100T Gateway'

Configuration decryption

Because a configuration file could be retrieved, I investigated its decryption path. Following the calls led to /usr/lib/lua/wfr/webutil.lua.

CODE
/export -> handleExport() -> encrptyconfig

Encryption is implemented in /usr/lib/lua/transformer/shared/ConfigCommon.lua. Background research showed that this encryption scheme was open source and had already been reverse engineered. GitHub - antnks/technicolor-config-decrypt: Technicolor router config decryption and injection exploit The earlier vulnerability appeared to have been fixed: the support account could no longer use it to obtain root. The web service now ran as admin, which likely faced the same restriction. The decryption method was unchanged, but required the following device-side file:

CODE
local rip_path = "/proc/rip/"
local rip_random_B = "0108"

def read_header(file):

Prior research describes the key file as follows:

CODE
key = read("/rip/0108",64)
aeskey = key[32:]
hmackey = key # Signs the configuration content; the value is checked even for a plaintext configuration upload.

The key file is not normally readable, so decryption requires either obtaining it or reproducing its contents. I suspected that the key might differ per device, but that a customized derivation could still be recoverable. Two experiments could test this: obtain shells on different devices and compare the files, or reverse engineer the derivation algorithm. Comparison alone would not settle the issue. Even if two RIP keys differed, they might still be derived from an accessible value such as the serial number. Understanding the derivation was therefore necessary.

Key investigation: comparing devices

The comparison approach requires two devices. Proposed experiments: Experiment one: Obtain a shell on each device and compare /proc/rip/0108. If the contents match, the comparison is complete. If they differ, continue the investigation. Experiment two: On one device, compare the file before and after a reboot and a factory reset.

This requires a root shell or another way to load the RIP kernel module separately. Because shell access was difficult, this approach was paused. In a decryption test, I used: Decryption succeeded for some configuration files but not all of them. This suggested that the random value differs between boards, motivating analysis of whether the value can be reproduced. The value survived reboot and factory reset, suggesting that it belonged to the board rather than the firmware image. Its provisioning path still needed to be located.

Key investigation: static reverse engineering

Following the earlier clues and string references placed the relevant implementation in the kernel module /lib/modules/4.1.38/ripdrv.ko. Static analysis showed:

C
int __fastcall randomkeyB(int a1, int a2)
{
  _DWORD v4[16]; // [sp+14h] [-48h] BYREF; each DWORD occupies four bytes.

  if ( a2 < 64 )
    return 0;
  sub_D18("RandomKeyB", v4); // First 32 bytes: 256 bits.
  sub_D18("UpperHalfOfRandomKeyB", &v4[8]); // The next 32 bytes, despite the "UpperHalf" name.
  memcpy(a1, v4, 64); // Copy 64 bytes from v4 to a1.
  return 64;
}

The output is written here. Analysis of sub_D18:

C
  v6 = (void (__fastcall *)(_BYTE *, void *, int))sha256_desc[22];
  v6(v9, &clinkDrv_tchRandom, 32);
  v7 = strlen(a1);
  v6(v9, a1, v7);
  ((void (__fastcall *)(_BYTE *, _DWORD *))sha256_desc[23])(v9, a2);
  return _stack_chk_guard;

The function uses SHA-256; I temporarily named it sha256_encryption. A SHA-256 digest is 32 bytes, suggesting that the HMAC key concatenates two digests. The following reconstruction was refined with GPT assistance:

C
// Function pointer types for clarity
typedef void (__fastcall *SHA256InitFunc)(_BYTE *);
typedef void (__fastcall *SHA256UpdateFunc)(_BYTE *, void *, int);
typedef void (__fastcall *SHA256FinalFunc)(_BYTE *, _DWORD *);
// Function pointers
SHA256InitFunc sha256_init = (SHA256InitFunc)sha256_desc[21];
SHA256UpdateFunc sha256_update = (SHA256UpdateFunc)sha256_desc[22];
SHA256FinalFunc sha256_final = (SHA256FinalFunc)sha256_desc[23];
// Initialize the output buffer to zero
memset(a2, 0, sizeof(int) * 8);
// Initialize the SHA-256 context
sha256_init(v9);
// Update the SHA-256 context with a constant value
sha256_update(v9, &clinkDrv_tchRandom, 32);
// Update the SHA-256 context with the input string
size_t input_length = strlen(a1);
sha256_update(v9, a1, input_length);
// Finalize the SHA-256 computation and store the result in 'a2'
sha256_final(v9, a2);

The approximate derivation flow is:

C

The source of clinkDrv_tchRandom was located in /lib/modules/4.1.38/bankmgr.ko.

C
  mtd_device_nm = get_mtd_device_nm("nvram");

The mtd_read prototype is:

C
ssize_t mtd_read(struct mtd_info *mtd, loff_t offset, size_t size, size_t *retlen, u_char *buf);

The reconstructed function is:

CODE
mtd_read(dev,offset,read_size,retvalue,destnation)

In essence, it reads 0x40 bytes from offset 0x1c100 in the nvram device and uses them as random-value material. This produced the following overall derivation model:

C
clinkDrv_tchRandom = mtd_read(0x1C100,0x40)
AESKEY_base = "RandomKeyB"
HMACKEY_base = "UpperHalfOfRandomKeyB"

AESKEY = sha256(clinkDrv_tchRandom+AESKEY_base)# The exact role of the two update calls still needed clarification at this stage.
HMACKEY = AESKEY + sha256(clinkDrv_tchRandom+HMACKEY_base)

The remaining question was whether the NVRAM value at 0x1c100 was fixed. The investigation tracked two tasks:

  • Determine the effect of the two update calls.
  • Determine how tchRandom is obtained. The following issue provided another clue: Command request · Issue #343 · Ansuel/tch-nginx-gui · GitHub That experiment reports a fixed value at /rip/0120. The corresponding identifier is RIP_ID_OSIK. Discussion with another researcher suggested that this value normally remains unchanged. Inspect /proc/mtd:
CODE

The corresponding block device is /dev/mtd4. Extracting mtd4 revealed tch_dsl_v01.0 near the beginning and tch_c1100t near the end. The device identifier is labeled boardnum. The 64-byte value raised a further question: was it generated during initialization or provisioned from another image? Block-device writes would normally go through mtd_write. Because mtd4 includes device-specific identifiers, my initial hypothesis was that this content was not simply copied from a generic firmware image. I investigated initialization next. One candidate NVRAM-write path was /usr/lib/libbcm_flashutil.so, but it did not contain the relevant write. Another candidate was /private/libcms_cli.so. An older kernel version pointed to /bin/persist_init. The implementation was located in vmlinux, under broad_ioctl: This still wrote to the NVRAM MTD device. I continued examining other write paths: The apparent write location instead looked like another read:

The value appeared to originate from hardware provisioning. A comparable implementation is cfe-bcm63xx/hostTools/nvramembed.c.

The BCM63xx CFE binaries provided further context. In one binary, the first part matched the contents of mtd4, while the second contained compressed cferam.000 data. This argued against generation by the running device software and suggested provisioning through: The write path remained a hypothesis, but the investigation established several useful observations:
CODE

This value is central to the device's authentication logic. Recovering it, or reproducing its derivation if it is algorithmic rather than independently random, could potentially affect authentication across related devices. That broader implication remained conditional.
The working hypothesis was that the device manufacturer provisions the random value through the SoC or board storage. Reversing web requests

Requests after login are encrypted. Understanding the algorithm is necessary to decrypt responses or modify requests. The recovered encryption flow is:

CODE
IV = requestIV
data = requestbody
KEY = header.apikey

AES.CCM(IV,KEY,data)

A corresponding encryption and decryption script:

PYTHON
#!/usr/bin/env python

import json
import base64
from cryptography.hazmat.primitives.ciphers.aead import AESCCM

def aes_ccm_decrypt_from_json(key, json_str):
    # Parse the JSON string
    data = json.loads(json_str)

    # Extract the values
    iv = base64.b64decode(data['iv'])
    ciphertext_and_tag = base64.b64decode(data['ct'])
    tag_size_bits = 64  # Tag size in bits
    tag_size_bytes = tag_size_bits // 8

    # Separate the ciphertext and the tag
    ciphertext = ciphertext_and_tag[:-tag_size_bytes]
    tag = ciphertext_and_tag[-tag_size_bytes:]

    # Perform decryption
    aesccm = AESCCM(key, tag_length=tag_size_bytes)
    try:
        plaintext = aesccm.decrypt(iv, ciphertext + tag, None)
        return plaintext
    except Exception as e:
        print(f"Decryption failed: {e}")
        return None

def aes_ccm_encrypt_to_json(key, plaintext, iv=None):
    # Generate a random IV if not provided
    if iv is None:
        iv = os.urandom(12)  # AES-CCM typically uses a 12-byte IV

    # Set the tag size (in bytes)
    tag_size_bytes = 8  # Corresponds to a 64-bit tag

    # Create AESCCM object
    aesccm = AESCCM(key, tag_length=tag_size_bytes)

    # Perform encryption
    ciphertext_and_tag = aesccm.encrypt(iv, plaintext, None)

    # Combine ciphertext and tag
    ciphertext = ciphertext_and_tag[:-tag_size_bytes]
    tag = ciphertext_and_tag[-tag_size_bytes:]

    # Encode the IV, ciphertext, and tag in base64
    iv_b64 = base64.b64encode(iv).decode('utf-8')
    ct_b64 = base64.b64encode(ciphertext + tag).decode('utf-8')

    # Create the JSON structure
    encrypted_data = {
        "iv": iv_b64,
        # "v": 1,
        # "iter": 10000,
        # "ks": len(key) * 8,  # Key size in bits
        # "ts": tag_size_bytes * 8,  # Tag size in bits
        # "mode": "ccm",
        # "adata": "",
        # "cipher": "aes",
        "ct": ct_b64
    }

    return json.dumps(encrypted_data)

Deriving the initial password from the random value

The algorithm can be recovered by reversing ripdrv.ko.

PYTHON
#/usr/bin/env python
#-*-coding:utf-8-*-

import hashlib

def getkey(input,clinkDrv_tchRandom):
    sha256 = hashlib.sha256()
    sha256.update(clinkDrv_tchRandom)
    sha256.update(input.encode('utf-8'))
    return sha256.digest()

def high_byte(value):
    return (value %3E> 24) & 0xff

def byte2(value):
    return (value >> 16) & 0xFF

def get_char_from_hash(hash_value):
    strings = "ABCDEFGHJKLMNPQRSTUVWXYZ"
    high_byte_value = high_byte(hash_value)
    index = high_byte_value % len(strings)
    return strings[index]

def sub_B2C(a1, a2, a3, a4, a6):
    a5 = []
    v18 = int.from_bytes(a1, byteorder='big')
    v15 = a4
    for _ in range(a6):
        v17 = v18 % v15 
        v18 //= v15 
        a5.append(a3[v17])
    a5.reverse()
    return ''.join(a5)

def traverse_string(s, start_char):
    start_index = s.index(start_char)
    left_part = s[start_index::-1]
    right_part = s[:start_index:-1]
    traversal_order = left_part + right_part
    
    return traversal_order
