CGI handlers implement the main request logic. The device uses a 32-bit x86 architecture.

Two main CGI binaries, index and cgibox, handle most of the application logic. Most CGI paths are symlinks to one of them, so these binaries and their shared libraries are the primary analysis targets.

The device looks up the supplied cookie in the session database. A matching entry authenticates the request. Otherwise, it checks whether REMOTE_ADDR is 127.0.0.1: a loopback request causes a session to be inserted, while other requests fail authentication. A successful login also inserts a session. X-Forwarded-For handling was not enabled.

This `pauth` value works and is inserted into the session database. An ordinary session is not inserted after a failed login. I therefore suspected an undocumented account, possibly derived from the device identifier. This remained a hypothesis.

The firmware returns this field during login, and the corresponding code can be located. My working hypothesis was that the cloud backend could obtain a management login using the device ID, while a local request could authenticate with the returned cookie. I found no firmware code setting or validating rwa_session_ic, suggesting that it belonged to the platform. The tentative model was: The device ID is bound to a LittleCloud session. The platform obtains a usable cookie using the device ID. rwa_session_ic may correspond to a changing request field on the platform. It did not appear to be an access token. An undocumented access mechanism was suspected, but not established.

Requests appeared to bypass normal validation when REMOTE_ADDR=127.0.0.1. Observed traffic flow: user requests -> couldserver -> ssh_sock -> localhost -> ssh_sock -> user response The firmware appeared to return a usable cookie when it recognized a request as local. Open question: What request does the cloud service send to the device during its initial binding? Hypothesis: The device ID is combined with .rwa21.peplink.com, for example: 293c-b16d-aab1-ic.rwa21.peplink.com This suggested that some device-side service receives the binding request, with a corresponding database record on the cloud server. Candidate attack surface one: Investigate the SSH credentials and whether ssh_sock provides a shell connection. Candidate attack surface two: locate the suspected undocumented firmware path and clarify its authentication logic. WTP appears to control traffic returned by ic2. WTP starts SSH, suggesting that the corresponding UDP port is externally reachable.
Working request-flow model: A user requests the device-specific cloud endpoint. The cloud service processes the request and forwards it to rwa21.peplink.com. An SSH remote-forwarding port relays it to port 80 on the device, then to its CGI handler. The handler sees a local request and bypasses the usual authentication check, creating the suspected unauthorized-access path.

Experimental attack design

At this stage, the experiment supported a man-in-the-middle position. Precondition: an administrator uses REMOTE_WEB in the IC2 platform, creating an SSH tunnel. Requests delivered through that tunnel reach the device without the usual authentication context.

Proposed experiment: Use a script to connect to the SSH tunnel and probe for an open forwarding port. If present, use the observed vulnerability to retrieve a configuration file and compare it with previously collected records, storing only new results. Repeat the observation after an interval.

Alternative approach: Investigate the AC program for a potential unauthenticated RCE path.

def evp_bytestokey(password: bytes, salt: bytes, key_len=32, iv_len=16):
    """
    Reproduce OpenSSL EVP_BytesToKey derivation (MD5, one iteration).
    """
    d = d_i = b''
    while len(d) %3C key_len + iv_len:
        d_i = hashlib.md5(d_i + password + salt).digest()
        d += d_i
    return d[:key_len], d[key_len:key_len+iv_len]

def main():
    fw_path = "firmware.bin"
    rsa_key_path = "rd"
    out_path = "firmware_decrypted.bin"

    print("[*] Starting Peplink firmware decryption...")

    # 1. Load the RSA private key using the recovered hardcoded passphrase.
    print(f"[*] Loading RSA private key: {rsa_key_path}")
    try:
        with open(rsa_key_path, 'rb') as f:
            rsa_key = RSA.import_key(f.read(), passphrase="NTM1NjgxaZ")
        cipher_rsa = PKCS1_v1_5.new(rsa_key)
    except Exception as e:
        print(f"[-] Failed to load RSA private key: {e}")
        return

    # 2. Read the encrypted firmware.
    print(f"[*] Reading firmware: {fw_path}")
    with open(fw_path, 'rb') as f:
        fw_data = f.read()

    # 3. Scan for the encrypted block's base offset.
    print("[*] Scanning the firmware header for the encrypted block base offset...")
    sentinel = b"RSA_DECRYPT_ERROR"
    base = -1
    passphrase = b""
    
    # Determine the RSA block size: 256 bytes for 2048-bit keys, 512 for 4096-bit keys.
    rsa_block_size = cipher_rsa._key.size_in_bytes()
    print(f"[*] RSA key length: {rsa_block_size * 8} bits")

    # Scan the first 64 KB for the correct start offset.
    for i in range(0, 65536):
        rsa_block_start = i + 4
        rsa_block_end = rsa_block_start + rsa_block_size
        rsa_block = fw_data[rsa_block_start : rsa_block_end]
        
        if len(rsa_block) != rsa_block_size:
            break
        
        try:
            # Attempt RSA private-key decryption.
            decrypted_raw = cipher_rsa.decrypt(rsa_block, sentinel)
            # A result other than the sentinel passes the initial decryption check.
            if decrypted_raw != sentinel:
                # Check that the passphrase is printable ASCII, usually ending in a newline.
                if b'\n' in decrypted_raw:
                    base = i
                    print(f"[+] Found base offset: {base} (0x{base:X})")
                    passphrase = decrypted_raw.split(b'\n')[0]
                    break
        except ValueError:
            # Skip offsets that produce a "Ciphertext too large" error.
            continue
        except Exception:
            # Handle other decryption exceptions.
            continue

    if base == -1:
        print("[-] No matching offset found. The block may be further into the file, or the file may be damaged.")
        return

    print(f"[*] Passphrase recovered from the RSA block: {passphrase.hex()} ({passphrase!r})")

    # 5. Extract the salt and derive the AES key and IV.
    salt_start = base + 522
    salt = fw_data[salt_start : salt_start + 8]
    print(f"[+] Salt: {salt.hex()}")

    aes_key, aes_iv = evp_bytestokey(passphrase, salt)
    print(f"[+] Derived AES-256 key: {aes_key.hex()}")
    print(f"[+] Derived AES-256 IV:  {aes_iv.hex()}")

    # 6. Decrypt the firmware payload.
    # The ciphertext follows the salt at base + 530.
    ciphertext_start = base + 530
    ciphertext = fw_data[ciphertext_start:]
    
    print(f"[*] Decrypting payload ({len(ciphertext)} bytes)...")
    cipher_aes = AES.new(aes_key, AES.MODE_CBC, aes_iv)
    plaintext_padded = cipher_aes.decrypt(ciphertext)

    # Remove PKCS7 padding.
    try:
        plaintext = unpad(plaintext_padded, AES.block_size)
    except ValueError:
        print("[-] Padding removal failed. The key may be incorrect or the file may contain an unencrypted trailer. Saving the unpadded result as-is.")
        plaintext = plaintext_padded

    # 7. Write the decrypted file.
    with open(out_path, "wb") as f:
        f.write(plaintext)
    
    print(f"[+] Firmware decrypted and saved to: {out_path}")
    
    # Optionally inspect the first bytes to identify the file type.
    file_magic = plaintext[:4]
    print(f"[*] Decrypted file magic: {file_magic.hex()} ({file_magic!r})")

if __name__ == "__main__":
    main()
